OpenAPI generator for a CLI: compile a Swagger spec into verbs

Most OpenAPI generators produce a typed client library in a language of your choice, and the command line tool on top is still yours to write. declick reads an OpenAPI 3 or Swagger 2 spec, JSON or YAML, and writes the CLI directly: one named verb per operation, one JSON envelope on every call, five exit codes, and a SKILL.md so an AI agent finds the tool without being told. The live Swagger Petstore spec compiles to 19 verbs whose whole surface is 1,583 characters.

How do I turn an OpenAPI spec into a CLI?

Install declick, run declick add with the spec's path or URL and a name, and the adapter exists. The first call after that is describe, which prints every verb with its one-line purpose and required arguments in under 2,000 characters. A spec-shaped URL, one with .json, .yaml, openapi, swagger or api-docs in the path, routes to the openapi engine even when the spec lists components first. A URL that answers 404 fails naming the status, and a plain web page is told it is not a spec rather than compiled as one.

What does a generated verb return?

Every verb returns the same envelope. Success is {"ok":true,"data":...,"meta":{"count":N,"truncated":false}} and failure is {"ok":false,"error":"...","exit":N}, with the API's error body carried in data when there is one. JSON is the default whenever stdout is not a terminal. The exit code is 0 for ok, 1 for an error, 2 for not found, 3 for blocked and 4 for auth needed, and it is the same five on every engine and on declick itself. --fields a,b projects named fields with dotted paths, --limit N caps a list, --where k=v filters it first, and --max-bytes N caps data at 8,192 bytes by default.

How does the generated CLI handle API keys?

The manifest stores the name of the environment variable, never its value. Petstore's get-pet-by-id declares an API key in the spec, so without PETSTORE_API_KEY set it exits 4 and names the key it wants. At run time declick reads process.env first, then ~/.creds/vault.env, for only the names the verb needs. A key is released only to the origin the adapter was built against; a request to another host exits 4 unless the change is explicit on the command line. --dry-run on any mutating verb prints the request it would send, with secrets shown as their env names, and sends nothing.

What about a spec with hundreds of operations?

Subset it at compile time. --verbs a,b keeps named operations and --tag t keeps one tag's worth, so an agent's surface stays under the 2,000-character ceiling that declick lint enforces. A surface over the ceiling pages itself: describe ends with a footer naming how many verbs are left and the flags that reach them, --grep text, --offset N and --verb v. The HTTP request flags are the same on every openapi adapter: --header, --base-url or --server, --body @file, --output for a binary response, --retry, --timeout and --verbose.

How is this different from openapi-generator or Speakeasy?

Those produce a library per language and leave the CLI, the output shaping and the exit codes to you. declick skips the library and writes the CLI, and the same command compiles a GraphQL endpoint, an MCP server, a Postman or Insomnia collection, a HAR capture, a SQLite file, another tool's --help, a browser page or a Windows app to the same contract. Runtime REST clients built for a person at a keyboard, restish among them, give you shorthand syntax and colored output for one API at a time; declick is built for a program that needs one shape it can parse every time.
